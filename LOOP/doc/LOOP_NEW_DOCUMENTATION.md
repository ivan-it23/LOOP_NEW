# LOOP_NEW — Техническая документация

## Дата актуализации
2026-06-23

## Назначение проекта
`LOOP_NEW` — измерительное приложение (C++/CLI, Windows Forms) для калибровки скважинных
приборов индукционного каротажа на калибровочном кольце. Приложение опрашивает прибор
по COM-порту, получает разности фаз между передатчиками на двух частотах (400 кГц и
2000 кГц), рассчитывает УЭС (удельное электрическое сопротивление) от параметров кольца
и отображает результаты в реальном времени.

Поддерживаются приборы трёх типов:
- **SDR** — опрос по COM-порту (baud 115200)
- **LWD1DDS** — опрос по COM-порту (baud 125000)
- **AUTONOM** — опрос через DLL `AMK_1DDS_AUTONOM.dll`

## 1. Архитектура данных: универсальные структуры GP_TOOL

Приложение использует универсальные структуры `GP_TOOL_DATA` и `GP_TOOL_METROLOGY`,
поддерживающие приборы с 3/4/5 передатчиками через динамическое определение `N_Tx`
из сигнатуры прибора.

### 1.1. `GP_TOOL_DATA` (240 байт, `#pragma pack(push, 1)`)

```c
struct GP_TOOL_DATA {
    uint32_t signature;
    uint32_t condition;
    uint32_t frame;
    float temperature;
    float rho_smt[2][5];       // УЭС на контроллере: [400, 2000][T1-T5]
    float phase_smt[2][5];     // симметризованные фазы: [400, 2000][T1-T5]
    float AM_RX_1[2][5];       // амплитуды первого приемника
    float ZERO_AM_RX_1[2];     // амплитуды RX1 при молчащих передатчиках
    float AM_RX_2[2][5];       // амплитуды второго приемника
    float ZERO_AM_RX_2[2];     // амплитуды RX2 при молчащих передатчиках
    float DELTA_PH[2][5];      // сырая разность фаз: [400, 2000][T1-T5]
    float ZERO_dPH[2];         // разность фаз молчащих передатчиков
};
```

### 1.2. `GP_TOOL_METROLOGY` (240 байт, `#pragma pack(push, 1)`)

```c
struct GP_TOOL_METROLOGY {
    uint32_t signature;
    uint32_t serial;
    uint16_t L1[5];            // расстояние до ближнего приемника, T1-T5
    uint16_t L2[5];            // расстояние до дальнего приемника, T1-T5
    uint16_t F[2];             // частоты: [0]=400 кГц, [1]=2000 кГц
    int16_t Air_zz[2][5];      // воздушные поправки фаз: [freq][Tx], mG
    int16_t Air_zz_amt[2][5];  // пороги амплитуд: [freq][Tx]
    uint32_t D_sonde_mm;
    uint32_t work_type;
    uint32_t Rx_Position;      // 0 = R1->T1, 1 = R1->T2
    uint16_t service[78];
};
```

### 1.3. Вспомогательные структуры
- `V10` (40 байт, `VALUE[10]`) — универсальный контейнер результатов
- `PHASE_ORIENTATION_DEBUG` — диагностический снимок ориентации фаз:
  `raw_delta`, `raw_normalized`, `orientation_sign`, `final_phase`
- `INC_SET` — параметры калибровки
- `ARGB` — цветовая модель для графиков
- `SONDE_PARAM` — параметры зонда (L1, L2, F)
- `LOOP_PARAM` — параметры кольца (R, r, Re, R_Add_Wire)

## 2. Индексация (freq-major, N_Tx из сигнатуры)

### 2.1. Определение N_Tx

```c
uint32_t buff = (signature << 12) >> 12;
uint32_t N_Tx = (buff % 100000) / 10000;  // toolCode, средняя цифра
if (N_Tx < 3 || N_Tx > 5) N_Tx = 5;        // безопасный фолбэк
```

### 2.2. Раскладка V10

Линейный индекс: `VALUE[freq * N_Tx + Tx]`
- `freq = 0` → 400 кГц, `freq = 1` → 2000 кГц
- `Tx = 0..N_Tx-1` → передатчики

Эта раскладка совпадает с порядком `sonde_param`, формируемым в `metro_convert`
(freq-major, страйд = N_Tx).

## 3. COM-протокол обмена с прибором

### 3.1. Структура пакета

```
[CMD:1][DATA:length][CRC16:2]
```

- `CMD` — байт команды
- `DATA` — полезная нагрузка (для опроса данных `length = 242`)
- `CRC16` — контрольная сумма (Modbus CRC16) по `CMD + DATA`

Полный пакет ответа при опросе данных: `245` байт (`1 + 242 + 2`).

### 3.2. Команды (из `variable.h`)

| Команда | Значение | Назначение |
|---------|----------|------------|
| `CMD_GET_DATA` | `0x01 \| KEY` (0x11) | Получить кадр данных |
| `CMD_GET_SIGNATURE` | `0x16` | Получить сигнатуру прибора |

`CMD` для опроса: `0x00` для SDR, `CMD_GET_DATA` (0x11) для LWD1DDS.

### 3.3. Параметры COM-порта

| Параметр | Значение | Где задаётся |
|----------|----------|--------------|
| BaudRate (SDR) | 115200 | `WorkForm.h` |
| BaudRate (LWD1DDS) | 125000 | `WorkForm.h` |
| ReadTimeout | 2000 мс | `WorkForm.h` |
| WriteTimeout | 2000 мс | `WorkForm.h` |

## 4. Цикл опроса: send_to_tool / receive_from_tool / get_ph_from_tool

### 4.1. `send_to_tool`
Формирует пакет `[CMD][DATA][CRC16]`, рассчитывает CRC16 по `CMD + DATA` и пишет в
COM-порт. Возвращает `0` при успехе, `1` при исключении.

### 4.2. `receive_from_tool`
Читает ответный пакет и проверяет CRC. Возвращает:
- `0` — успех (CRC валиден), `DATA` заполнен
- `1` — таймаут / неполный пакет
- `2` — ошибка CRC

**Критически важная деталь чтения (см. раздел 7):** `SerialPort::Read` в .NET
возвращает управление, как только доступен хотя бы один байт, и **не блокирует** до
получения всех запрошенных байт. Поэтому чтение выполнено циклом с накоплением:

```cpp
const int total = length + 3;
int bytes_read = 0;
DateTime deadline = DateTime::Now.AddMilliseconds(COM->ReadTimeout);
try {
    while (bytes_read < total) {
        int n = COM->Read(packet_to_receive, bytes_read, total - bytes_read);
        if (n <= 0) break;
        bytes_read += n;
        if (DateTime::Now > deadline) break;
    }
}
catch (...) {
    if (bytes_read == 0) stop = 1;   // TimeoutException — данных нет
}

if (!stop && bytes_read < total) {
    // неполный пакет → таймаут (res=1), буфер очищается
    COM->DiscardInBuffer();
    return 1;
}
```

### 4.3. `get_ph_from_tool` (унифицированный опрос SDR и LWD1DDS)
Алгоритм:
1. Проверка открытости порта.
2. Очистка входного буфера (`DiscardInBuffer`) от «хвостов» предыдущих обменов.
3. Отправка команды опроса (`send_to_tool`).
4. Приём ответа (`receive_from_tool`).
5. При успехе — копирование `GP_TOOL_DATA`, извлечение `DELTA_PH[freq][Tx]`,
   нормализация к `[-PI, PI]` и применение знака ориентации по `Tx` и `Rx_Position`
   через `fill_phase_from_tool_data`.
6. При таймауте — **один автоматический повтор** (`MAX_RETRIES = 1`).

`CMD` передаётся в `receive_from_tool` по ссылке (`uint8_t&`), чтобы вызывающая
сторона видела реальный командный байт ответа.

## 5. Логика ориентации фаз и `Rx_Position` (2026-06-23)

Текущий формат кадра прибора содержит `DELTA_PH[2][5]`, а не отдельные массивы
`PH_RX_1` / `PH_RX_2`. Поэтому логика старого рабочего кода адаптирована как правило
знака поверх сырого `DELTA_PH`.

### 5.1. Эталонная логика коллеги для положения `R1->T1`

Старый стабильный код считал разность фаз так:

```cpp
ph_data.VALUE[T1] = PH_RX_2[T1] - PH_RX_1[T1];
ph_data.VALUE[T2] = PH_RX_1[T2] - PH_RX_2[T2];
ph_data.VALUE[T3] = PH_RX_2[T3] - PH_RX_1[T3];
ph_data.VALUE[T4] = PH_RX_1[T4] - PH_RX_2[T4];
ph_data.VALUE[T5] = PH_RX_2[T5] - PH_RX_1[T5];
```

В `LOOP_NEW` это соответствует шаблону знака относительно `DELTA_PH`:

| `Rx_Position` | Геометрия | T1 | T2 | T3 | T4 | T5 |
|---------------|-----------|----|----|----|----|----|
| `0` | `R1->T1` | `+` | `-` | `+` | `-` | `+` |
| `1` | `R1->T2` | `-` | `+` | `-` | `+` | `-` |

Знак зависит именно от номера передатчика `Tx`, а не от линейного индекса `VALUE`.
Это критично для пятизондовых приборов: при `N_Tx = 5` вторая частота начинается с
индекса `5`, и старая проверка четности линейного индекса давала неверный знак.

### 5.2. Реализация в коде

Основные функции находятся в `function.cpp`:

- `normalize_phase` приводит фазу к диапазону `[-PI, PI]`.
- `normalized_rx_position` трактует все значения, кроме `1`, как безопасное значение `0`.
- `rx_phase_orientation_sign(Tx, rx_position)` возвращает `+1` или `-1`.
- `apply_rx_phase_orientation(raw_phase, air_phase, Tx, rx_position)` нормализует сырую фазу,
  вычитает воздушную поправку, применяет знак ориентации и повторно нормализует результат.
- `fill_phase_from_tool_data(GP_TOOL_DATA*, V10&)` заполняет `ph_data.VALUE` и
  диагностическую структуру `phase_orientation_debug`.

Единая логика применяется в путях:

- `get_ph_from_tool` — основной live-опрос SDR/LWD1DDS.
- `get_ph_from_1DDS` — совместимый путь LWD1DDS.
- `get_ph_from_SDR` — совместимый путь SDR.
- `get_ph_from_AUTONOM` — DLL-опрос AUTONOM.
- `get_phase` и `get_phase_smt` — пересчет фаз с учетом `Air_zz`.

### 5.3. Метрология и UI

`GP_TOOL_METROLOGY::Rx_Position` хранит положение первого приемника:

- `0 - R1->T1`
- `1 - R1->T2`

В окне метрологии (`MetroForm`) добавлено поле выбора позиции приемника. Значение
считывается из прибора/файла метрологии, отображается в UI и записывается обратно при
сохранении или записи метрологии в прибор.

### 5.4. Единый опрос приборов и определение типа из сигнатуры (2026-06-23)

Ранее тип прибора выбирался вручную в комбобоксе `Тип прибора` (`LWD_1DDS`/`SDR`/`AUTONOM`)
и разветвлял логику включения и опроса. Это устранено: все приборы используют **единый
COM-алгоритм опроса** (ранее путь `LWD_1DDS`), а тип определяется из сигнатуры.
SDR является модификацией Автономного прибора и не требует отдельного пути.

Реализация (`WorkForm.h`), по образцу `Amk-Horizon-New-Chart` (`SerialModule`/`UniversalCanonicalAdapter`):

- **Единый путь включения** (`button_ON_OFF_Click`): `BaudRate = 125000`,
  `ReadTimeout/WriteTimeout = 2000`, чтение метрологии командой `0x13`, `metro_convert`.
- **Единый опрос** (`sonde_read_timer`): всегда `get_ph_from_tool(serialPort_sonde, CMD_GET_DATA, ...)`,
  где `CMD_GET_DATA = 0x01 | 0x10 = 0x11` (совпадает с эталонным `CMD_DATA`).
- **Тип из сигнатуры**: `SetDetectedToolType(signature)` декодирует `device_type = low20/100000`
  (`1 = Автономный`, `2 = LWD`) и `N_Tx`, выводит строку вида `"LWD 5TX"` / `"Автономный 4TX"`
  в комбобокс-индикатор (`DropDownStyle = DropDownList`, заполняется программно).
- Комбобокс больше **не управляет** логикой: `comboBox_tool_type_SelectedIndexChanged` —
  no-op, тип в `Conf.txt` не восстанавливается.

Dormant-код (DLL-путь `AMK_*` для AUTONOM, специализированные `get_ph_from_SDR`/
`get_ph_from_1DDS`/`get_ph_from_AUTONOM`, SDR-ветка метрологии) сохранён через `if (false)`
для возможного будущего использования и не участвует в живом потоке.

## 6A. Симметризация фаз (2026-06-23)

Логика симметризации фаз (`get_phase_smt`, `get_air_smt` в `function.cpp`) портирована
из эталонного проекта `Amk-Horizon-New-Chart` и больше не захардкожена под 4 передатчика.

### 6A.1. Определение числа передатчиков
`N_Tx` берётся из сигнатуры через `decode_tool_signature` (раздел 2.1), поддерживаются
приборы с 3/4/5 передатчиками. Раскладка результата — freq-major со страйдом `N_Tx`:
`phase_smt.VALUE[freq * N_Tx + t]`. Для приборов с `N_Tx < 5` выходы для
несуществующих передатчиков всегда нулевые.

### 6A.2. Выбор матрицы по маске работающих передатчиков
Матрица симметризации `K` выбирается диспетчером `build_symmetry_matrix(K, N_Tx, condition)`:
- `condition` — 8-битная маска работающих передатчиков (bit0 = T1 … bit4 = T5),
  извлекается из 32-битного поля `GP_TOOL_DATA::condition` функцией `extract_condition_byte`
  (layout LSB-first: byte0 = 2000 кГц, byte1 = 400 кГц).
- Для `N_Tx = 5/4/3` используются специализированные наборы матриц
  (`build_symmetry_matrix_5tx/4tx/3tx`), покрывающие комбинации «все работают» и
  «один передатчик не работает».
- Для нераспознанных комбинаций применяется identity-матрица по маске `condition`
  (`fill_identity_symmetry_matrix`).

Прежняя логика выбора по биту `serial & (1 << 17)` удалена в пользу выбора по
`(N_Tx, condition)`.

### 6A.3. Подготовка входных разностей фаз
Входные `DELTA_PH[freq][Tx]` нормализуются к воздуху по `Air_zz[freq][Tx]` и получают
знак ориентации через `apply_rx_phase_orientation` (раздел 5.2), что сохраняет
поддержку `Rx_Position`. Для `Rx_Position = 0` знаки чередуются как `+,-,+,-,+`, что
совместимо с матрицами симметризации эталона.

## 7. История диагностики и исправления serial-протокола (2026-06-16)

### 7.1. Симптом
При опросе LWD1DDS наблюдались постоянные ошибки CRC (`res=2`), затем — после первых
правок — постоянные таймауты (`res=1`) с сообщениями `timeout (short read: 1/245)`,
несмотря на то что `BytesToRead` показывал наличие данных в буфере.

### 7.2. Путь диагностики
1. Добавлено подробное логирование `BytesToRead`, hex-дампа пакета, CRC и таймаутов.
2. Увеличены таймауты с 200 мс → 1000 мс → 2000 мс.
3. Добавлен retry при таймауте.
4. **Корневая причина найдена** по строке `BytesToRead=245 need=245` +
   `timeout (short read: 1/245)`: данные физически были в буфере, но единичный вызов
   `COM->Read(...)` возвращал лишь 1 байт.

### 7.3. Корневая причина
`System::IO::Ports::SerialPort::Read(buffer, offset, count)` по спецификации .NET
возвращается, как только доступен **хотя бы один** байт, и не ждёт получения всех
`count` байт. Однократное чтение трактовало частичный приём как таймаут.

### 7.4. Исправление
Чтение в `receive_from_tool` переписано на **цикл накопления байт с дедлайном**
(см. раздел 4.2), по образцу `ReceivePacket` из эталонного проекта
`Amk-Horizon-New-Chart`. После этого опрос стабильно возвращает `res=0` с корректными
фазами.

### 7.5. Сопутствующие правки
- `ReadTimeout` / `WriteTimeout` = 2000 мс (`WorkForm.h`).
- Убран `Sleep(50)` перед чтением в `get_ph_from_tool` (не требовался при цикле чтения).
- Добавлен один автоматический retry при таймауте.
- Убраны лишние `DiscardInBuffer` / `DiscardOutBuffer`, приводившие к потере данных.

## 8. Система логирования

Подробное логирование пишется в `LoopDeviceLog.txt` (каталог приложения) и дублируется
в `cout`.

### 8.1. Логируемые события включения прибора
- Тип прибора, BaudRate, открытие порта
- Чтение метрологии: signature, serial, N_Tx, частоты `F[0]/F[1]`, длины `L1/L2`,
  воздушные поправки `Air_zz`, позиция `Rx_Position`
- Конвертация в `sonde_param`
- Результат включения

### 8.2. Логируемые данные при опросе (каждый кадр)
- `ReadTimeout`, `WriteTimeout`, `BytesToRead` перед опросом
- `[receive_from_tool] BytesToRead / need / ReadTimeout`
- Результат `res` (0 = успех)
- Полученные фазы `ph_data.VALUE`: индекс, частота, Tx, значение в рад и mG
- Диагностика `PH_ORIENTATION_DEBUG`:
  `raw_DELTA_PH`, нормализованное сырое значение, примененный `orientation_sign`,
  итоговый `final_ph_data`
- Вычисленное УЭС `ro_data.VALUE` (в рабочем режиме)

### 8.3. Анализ последних актуальных сессий (2026-06-23)

Ориентир для продолжения отладки:

- Последние рабочие сессии использовали LWD1DDS, серийный номер `12026`, сигнатуру
  `0x24dd9`, `N_Tx = 5`, `Rx_Position = 0`.
- В сессиях 15:26:43 и 15:27:21 опрос шел стабильно с `res=0`.
- В сессии 15:39:15 было около 800 успешных чтений, затем после позиции примерно
  `R_IDX=8`, `C_IDX=6` начались ошибки `res=3`.
- `res=3` в текущем `get_ph_from_tool` означает закрытый COM-порт (`COM->IsOpen == false`),
  поэтому финальная проблема той сессии похожа на потерю/закрытие порта, а не на знак фазы.
- После записи локального воздуха высокочастотные каналы T4/T5 на 2000 кГц давали
  отрицательные скорректированные фазы при положительных ожидаемых значениях; это следует
  проверять через новый `PH_ORIENTATION_DEBUG`, чтобы отделить ошибку знака от локального
  воздуха и физики измерения.

### 8.4. Рекомендации по использованию
1. Перед тестом удалить старый `LoopDeviceLog.txt`.
2. Запустить приложение, нажать «ВКЛЮЧИТЬ ПРИБОР».
3. Проверить лог в каталоге приложения.
4. При отладке фаз смотреть связку `raw_DELTA_PH` → `orientation_sign` →
   `final_ph_data`.
5. Для продакшена ограничить подробное логирование ошибками или добавить ротацию.

## 9. Эталонный проект Amk-Horizon-New-Chart

При возникновении проблем с протоколом обмена, парсингом данных или метрологией следует
сверяться с эталонным проектом `Amk-Horizon-New-Chart`, который реализует ту же
предметную область в более зрелой архитектуре.

### 9.1. Ключевые файлы эталона

| Файл / Символ | Что описывает | Применимость к LOOP_NEW |
|---------------|---------------|-------------------------|
| `SerialModule.cpp` → `ReceivePacket` | Чтение пакета циклом с дедлайном до набора всех байт | Образец для `receive_from_tool` (раздел 4.2) |
| `SerialModule.cpp` → `ConfigureOpenedSerialHandle` | Настройка `COMMTIMEOUTS` (ReadTotalTimeoutConstant = 1000, multiplier = 10) | Обоснование таймаутов |
| `SerialModule.cpp` → `RequestData` | Отправка команды + приём `GP_TOOL_DATA` + валидация + парсинг | Образец цикла опроса |
| `SerialModule.cpp` → `RequestMetrology` | Запрос метрологии `CMD_GET_METROLOGY`, ретраи | Образец чтения метрологии |
| `SerialModule.cpp` → `LegacyPollingLoop` | Цикл опроса с реконнектом и обработкой stale-handle | Образец устойчивого опроса |
| `DataModule.cpp` | Управление и парсинг кадров в `ParsedToolFrame` | Подход к парсингу |
| `ToolDataAdapters.cpp` | Адаптер-парсинг: декодирование toolCode, определение N_Tx и числа передатчиков | Образец универсальной обработки 3/4/5 Tx |
| `doc/COM_5TX_GP_POLLING_AND_METROLOGY.md` | Протокол COM-опроса и метрологии: формат пакета, команды, baud, поток подключения, обработка ошибок | Справочник по протоколу |

### 9.3. Конвенции, общие для обоих проектов
1. **N_Tx из сигнатуры** — не хардкодить число передатчиков.
2. **Freq-major индексация** — `[freq * N_Tx + Tx]` во всех массивах результатов.
3. **F[2]** — две рабочие частоты (400 кГц, 2000 кГц).
4. **Air_zz[2][5]** — фаза в воздухе как `[freq][Tx]`; UI маппит линейные индексы на `[freq][Tx]`.
5. **Rx_Position** — положение приемников влияет на знак разности фаз.
6. **Sign-flip** — знак зависит от `Tx` и `Rx_Position`: для `R1->T1` шаблон
   `+,-,+,-,+`, для `R1->T2` шаблон `-,+,-,+,-`.
7. **Чтение serial** — цикл накопления байт с дедлайном, а не однократный `Read`.

## 10. Замечания и риски

1. **Мёртвый код**: `MyForm2.h` / `MyForm3.h` ссылаются на устаревшую модель и не компилируются. Активация потребует отдельного рефакторинга.
2. **DLL AUTONOM**: предполагается, что `AMK_1DDS_AUTONOM.dll` / `AMK_GetData` возвращают данные в формате `GP_TOOL_DATA` (240 байт). Отладка DLL — отдельная задача.
3. **Сборка**: проект C++/CLI; требуется полная перекомпиляция после изменений. В текущем окружении MSBuild доходит до компиляции новой фазовой логики, но общая сборка может останавливаться на старых Unicode WinAPI-вызовах в `WorkForm.h` (`char*`/`LPCWSTR`), не связанных с доработкой фаз.
4. **UI Air**: MetroForm отображает 10 текстбоксов под `Air_zz`; при `N_Tx < 5` часть полей неактуальна (legacy-особенность, UI их не скрывает).
