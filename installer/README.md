# Установщик приложения "Кольца"

Установщик собирается через Inno Setup 6 из Release-папки WinUI-приложения. Последний собранный поставочный артефакт имеет версию `1.1.8`.

Версия `1.1.8` сообщает пользователю о состоянии памяти кольца. При подключении кольца и прибора, по кнопке `Прочитать из кольца` и при отказе запуска `Режима АВТО` приложение называет пустые, непрочитанные и записанные не под этот прибор ячейки и порядок действий; в панели `Состояние кольца` появилась строка `Память`. Неудачное подключение кольца теперь сопровождается окном с причиной (порт занят, порта нет, устройство Bluetooth не отвечает). Уведомления показываются по очереди, а не отбрасываются, если окно уже открыто. Процент отклонения больше не усекается до целого на каждом кадре, и в таблице не появляется `−0,0 %`. Отключение прибора во время опроса не пишется в журнал как ошибка. Версия `1.1.7` до неё исправляла две ошибки заполнения памяти кольца. Во-первых, диапазон записи считался по числу каналов прибора и не учитывал смещение высокочастотного банка: у прибора на четыре передатчика на универсальном кольце ячейка `Z8` оставалась вне записи, и канал `T4` второй частоты навсегда сохранял чужую реактивность. Во-вторых, кнопка `Рассчитать` защищала от пересчёта любое непустое значение в поле `Реакт. изм.`, включая прочитанное из самого кольца, — приложение возвращало кольцу его же содержимое, и обойти это можно было только ручной очисткой поля. Теперь защищено ровно то, что введено с клавиатуры. Версия `1.1.6` до неё исправляла выцветание титульного блока вкладки `Документация`: белый заголовок на корпоративном тёмно-синем снова читается. Версия `1.1.5` до неё содержала исправления масштаба (вписывание содержимого в окно, набор значений `80/90/100%`, масштабирование всплывающих подсказок) и исправления автообновления: приложение снова открывается после обновления, загрузка не обрывается по тайм-ауту, установщик проверяется по SHA-256, а во вкладке `Проверить обновления` появилось ручное окно проверки. Более ранние локальные артефакты остаются в `installer\Output` как история сборок.

## Сборка

Скрипта сборки в проекте нет: установщик собирается двумя командами вручную.
Поэтому порядок ниже нужно выполнять целиком и в указанной последовательности —
пропуск любого шага даёт установщик, который выглядит собранным, но содержит не
то, что заявлено в имени файла.

### Что и откуда упаковывается

`setup.iss` берёт файлы из **каталога сборки**, а не публикации:

```text
src\LOOP.Next.App\bin\x64\Release\net10.0-windows10.0.26100.0\win-x64
```

Это выход `dotnet build -c Release -p:Platform=x64`. Приложение unpackaged
(`WindowsPackageType=None`) и self-contained по Windows App SDK
(`WindowsAppSDKSelfContained=true`), поэтому каталог сборки уже содержит всё
необходимое и отдельная публикация не нужна.

> **Не выполняйте `dotnet publish`.** В соседнем проекте «Визуализация данных»
> установщик собирается именно из каталога публикации, и по привычке эту команду
> легко перенести сюда. Здесь она бесполезна: `setup.iss` на каталог публикации
> не смотрит и упакует то, что осталось в `bin` от предыдущей сборки.

### Шаг 1. Выбрать номер версии

Номер должен быть выше последнего выпущенного и **не должен повторять уже
использованный**: клиент автообновления сравнивает версии, и другое содержимое
под прежним номером до пользователя может не дойти.

Каталог `installer\Output` исключён из git (`.gitignore`, строка
`installer/Output/`), поэтому история выпущенных номеров хранится только на
рабочей машине. Перед выбором номера посмотрите, что там уже лежит:

```powershell
Get-ChildItem installer\Output\Koltsa-Setup-*.exe | Select-Object Name, Length, LastWriteTime
```

### Шаг 2. Проставить номер в трёх местах

Версия не выводится автоматически — она записана в трёх файлах, и все три обязаны
совпадать:

| Файл | Что править |
| --- | --- |
| `src\LOOP.Next.App\LOOP.Next.App.csproj` | `Version`, `AssemblyVersion`, `FileVersion`, `InformationalVersion` |
| `installer\setup.iss` | `#define MyAppVersion` |
| `installer\koltsa-version.txt` | первая строка — номер, вторая — имя файла установщика, третья — SHA-256 установщика |

Что ломается при рассинхроне:

- забыли `csproj` — установщик называется новой версией, а внутри лежит `.exe`
  старой; установленное приложение продолжит предлагать себе же обновление по
  кругу;
- забыли `setup.iss` — файл получит имя предыдущей версии и перезапишет уже
  выпущенный артефакт;
- забыли `koltsa-version.txt` — обновление не предложится вовсе либо укажет на
  несуществующий файл;
- оставили в `koltsa-version.txt` SHA-256 от предыдущей сборки — приложение
  скачает установщик, увидит несовпадение суммы, откажется его запускать и
  сообщит об этом пользователю. Сумма считается в шаге 6, уже после сборки
  установщика, поэтому третья строка заполняется последней.

### Шаг 3. Очистить каталог сборки

`dotnet build` не удаляет файлы, исчезнувшие из проекта, а `[Files]` в
`setup.iss` копирует каталог целиком. Без очистки в поставку попадают библиотеки
и ресурсы, которых в проекте уже нет.

```powershell
Remove-Item -Recurse -Force src\LOOP.Next.App\bin\x64\Release -ErrorAction SilentlyContinue
```

### Шаг 4. Собрать Release и прогнать проверки

```powershell
dotnet restore LOOP_NEXT.sln
dotnet build LOOP_NEXT.sln -c Release -p:Platform=x64 --no-restore
& ".\tests\LOOP.Next.Hardware.ProtocolChecks\bin\Release\net10.0\LOOP.Next.Hardware.ProtocolChecks.exe"
```

Сборка обязана пройти с нулём ошибок и нулём предупреждений; протокольные
проверки — без единого провала. `--no-restore` допустим только после явного
`dotnet restore`.

### Шаг 5. Собрать установщик

```powershell
& "C:\Program Files (x86)\Inno Setup 6\ISCC.exe" installer\setup.iss
```

Путь к `ISCC.exe` зависит от установки Inno Setup 6; при другой разрядности или
каталоге поправьте его в команде. Готовый файл появится в
`installer\Output\Koltsa-Setup-<version>.exe`.

### Шаг 6. Проверить собранное

Скрипт ничего не проверяет за вас. Блок ниже сверяет три места с версией,
подтверждает версию внутри payload, ищет журналы в поставке, считает SHA-256 и
записывает файл-спутник:

```powershell
$version = (Select-String -Path installer\setup.iss -Pattern '#define MyAppVersion\s+"(.+)"').Matches[0].Groups[1].Value
$setup   = Get-Item "installer\Output\Koltsa-Setup-$version.exe"
$exe     = Get-Item "src\LOOP.Next.App\bin\x64\Release\net10.0-windows10.0.26100.0\win-x64\Кольца.exe"
$feed    = Get-Content installer\koltsa-version.txt

"setup.iss:      $version"
"csproj:         " + (([xml](Get-Content src\LOOP.Next.App\LOOP.Next.App.csproj)).Project.PropertyGroup.Version | Where-Object { $_ })
"payload .exe:   " + $exe.VersionInfo.FileVersion
"koltsa-version: " + ($feed -join ' / ')
"размер setup:   {0:N0} байт" -f $setup.Length
$hash = (Get-FileHash $setup.FullName -Algorithm SHA256).Hash
"SHA-256:        $hash"

# Журналы испытаний не должны попасть пользователям.
Get-ChildItem "src\LOOP.Next.App\bin\x64\Release\net10.0-windows10.0.26100.0\win-x64" -Recurse -Include *.log,LoopDeviceLog.txt |
  ForEach-Object { "ЛИШНИЙ ФАЙЛ В ПОСТАВКЕ: " + $_.Name }

# Файл-спутник с контрольной суммой создаётся вручную.
"$hash  $($setup.Name)" | Set-Content "$($setup.FullName).sha256" -Encoding ascii
```

Все четыре номера обязаны совпасть, лишних файлов быть не должно.

Папка `installer\Output` является локальным релизным выводом и игнорируется git.
Готовый `.exe` нужно загружать на хостинг или прикладывать к релизу вручную.

### Частые ошибки

- **`dotnet publish` вместо `dotnet build`** — упаковывается устаревший `bin`.
- **Версия поднята не везде** — см. таблицу в шаге 2.
- **Пропущена очистка `bin`** — в поставку попадают файлы удалённых сборок.
- **Повторно использован номер** — у пользователей обновление не появится.
- **Забыт файл-спутник `.sha256`** — контрольную сумму нечем сверить.
- **Загружен только установщик без `koltsa-version.txt`** — обновление не
  предложится; порядок публикации важен, см. чек-лист ниже.

## Текущий поставочный релиз 1.1.8

Локальный комплект выпуска:

```text
installer\Output\Koltsa-Setup-1.1.8.exe
installer\Output\Koltsa-Setup-1.1.8.exe.sha256
installer\Output\koltsa-version.txt
```

Проверенные метаданные:

- версия приложения: `1.1.8.0`;
- версия установщика: `1.1.8`;
- размер установщика: `62158948` байт;
- SHA-256: `F7AC62773B1E8D896A1AE1D9914EBF4D6291447EBCC62AA7DCB39FB329FFCBFD`;
- Release x64: `0` предупреждений, `0` ошибок;
- protocol checks: `98/98 passed`;
- журналов испытаний в каталоге поставки нет.

Не проверено на момент сборки: тихая установка, сквозное обновление с `1.1.7` и живое
автообновление. Аппаратный прогон с кольцом выполнен 25.09 до последних
правок (Картограф LWD 4Tx, кольцо 151): 28 точек из 28. Последние правки
(`−0,0 %`, окно отказа подключения, снятие окна о шуме) оператор проверил
в приложении перед сборкой, журналом эта проверка не подтверждена.

Сценарий `[Files]` исключает из поставки `LoopDeviceLog.txt`, `*.log`, `*.tmp` и `*.pdb`. Runtime-журнал испытаний из `src\LoopDeviceLog.txt` не должен попадать пользователям.

Предыдущий артефакт `1.1.7` имел размер `62151020` байт и SHA-256 `6C352F335665A38598BECEFF2FCA0181D8B08AAF8DC48D324E13F29D18948B72`.

## Автообновление

Приложение проверяет обновления при запуске по адресу:

```text
http://ivanbohg.beget.tech/FilesForProgramVisualisation/koltsa-version.txt
```

Формат `koltsa-version.txt`:

```text
1.1.8
Koltsa-Setup-1.1.8.exe
F7AC62773B1E8D896A1AE1D9914EBF4D6291447EBCC62AA7DCB39FB329FFCBFD
```

Третья строка с SHA-256 необязательна для совместимости с ранее выпущенными
файлами, но заполнять её нужно всегда. Установщик отдаётся по обычному HTTP и
запускается приложением автоматически: без сверки суммы подменённый по дороге
файл был бы выполнен молча. При несовпадении суммы приложение отменяет установку
и сообщает об этом пользователю.

В репозитории поддерживается готовый файл `installer\koltsa-version.txt` для последнего поставочного номера. При выпуске новой версии его нужно обновлять синхронно с `LOOP.Next.App.csproj` и `installer\setup.iss`.

Такой же файл лежит рядом с артефактом — `installer\Output\koltsa-version.txt`. Источником истины считается файл в `installer\`, потому что каталог `Output` исключён из git; копию в `Output` держите совпадающей с ним, чтобы не выложить на сервер устаревшую.

Установщик из второй строки должен лежать в той же папке:

```text
http://ivanbohg.beget.tech/FilesForProgramVisualisation/Koltsa-Setup-1.1.8.exe
```

Если версия на сервере выше текущей версии приложения, пользователь получает предложение скачать и установить обновление. Обновление запускается через скачанный Inno Setup установщик, чтобы обновлялись не только `Кольца.exe`, но и все DLL, ресурсы WinUI и ассеты приложения.

## Чек-лист публикации

1. Выбрать номер выше последнего опубликованного и синхронно изменить его в `LOOP.Next.App.csproj`, `setup.iss` и `koltsa-version.txt` — см. таблицу в разделе «Сборка».
2. Выполнить актуальные protocol checks и получить полный успешный результат без единого провала (число проверок растёт вместе с проектом; на 25 сентября 2026 года — `98/98`).
3. Очистить `bin\x64\Release`, собрать Release x64 и Inno Setup установщик; проверить отсутствие предупреждений и ошибок.
4. Проверить запуск установленного приложения и аппаратный smoke-тест с исправным кольцом: подключение, чтение сигнатуры по Bluetooth, чтение параметров и начало штатного workflow. `ZERASE` не включать в обязательный smoke-тест, поскольку это разрушающая параметры диагностическая команда.
5. Проверить имя, версию, размер и SHA-256 нового файла блоком проверки из раздела «Сборка» и убедиться, что все четыре номера совпали, а журналов в поставке нет.
6. Загрузить `Koltsa-Setup-<new-version>.exe` в `FilesForProgramVisualisation`.
7. После установщика загрузить актуальный `koltsa-version.txt` в ту же папку.
8. Проверить прямую доступность обоих URL.
9. Запустить установленную предыдущую версию и убедиться, что она предлагает обновление до нового номера.

На 2026-09-25 локально собран установщик `1.1.8`. Размер `62158948` байт, SHA-256 `F7AC62773B1E8D896A1AE1D9914EBF4D6291447EBCC62AA7DCB39FB329FFCBFD`. Проверены совпадение версии в трёх местах, версия внутри payload, отсутствие журналов в поставке и полный прогон protocol checks. Тихая установка и сквозное обновление для этого выпуска не проводились.

Загрузка на сервер не выполнена: пока `Koltsa-Setup-1.1.8.exe` и обновлённый `koltsa-version.txt` не лежат в `FilesForProgramVisualisation`, у пользователей обновление не появится.

## Раздача установщика и SmartScreen

Установщик не подписан сертификатом Authenticode. Файл, скачанный из интернета,
получает метку зоны, и при запуске неподписанного файла с такой меткой Windows
показывает окно `Windows защитила ваш компьютер`, где сразу видна только кнопка
отказа, а запуск скрыт за ссылкой `Подробнее`. Пользователь, закрывший это окно,
видит ровно то, что описывают как «установка не происходит».

Раздача в ZIP-архиве положение ухудшает: начиная с Windows 10 1809 проводник
переносит метку зоны с архива на извлечённые файлы, поэтому распакованный
`Koltsa-Setup-<version>.exe` наследует метку, и предупреждение появляется уже
после распаковки, когда пользователь считает файл локальным.

По убыванию надёжности:

1. Подписать установщик сертификатом Authenticode — единственное полное решение.
2. Раздавать `.exe` напрямую, без ZIP. Предупреждение останется, но появится
   один раз на файле, который пользователь осознанно скачал.
3. Снимать метку вручную: свойства файла, флажок `Разблокировать`, либо
   распаковка архиватором, не переносящим метку зоны.

Автообновления это не касается: приложение скачивает установщик само и снимает
метку зоны до запуска.
